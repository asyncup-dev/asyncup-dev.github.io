Configuration ​

AsyncUp is configured in two layers:

  1. Bootstrap: a handful of environment variables (database, port, the operator token, the encryption key). Set once, rarely touched. This page is the one reference for them.
  2. Everything else: managed in the web app under Settings and stored in your database, secrets encrypted (AES-256-GCM via SECRET_KEY). Changes apply immediately, no restart.

Changing a variable needs the container recreated, not just restarted: docker compose up -d --force-recreate asyncup.

Outbound webhooks ​

Give a standup a Webhook URL (Standup › Settings › Integrations) and AsyncUp POSTs JSON to it as things happen — the cheap path into Sheets (Apps Script), Zapier/n8n, or your own service:

EventWhenBody
submissionEvery submission and editstandup, date, user, answers, mood, late, edited
wrap_upThe run closesstandup, date, summary (same numbers as the posted wrap-up)
schedule_changeSomeone's week or days off changeperson, summary, who, channel — see Personal schedules
time_off_requestA request needs approvalperson, dates, working, reason, request ids
testSend test in the standup's settingsstandup

Deliveries time out after 5 s and failures are only logged — a dead webhook never breaks the standup.

Every delivery is signed: the X-AsyncUp-Signature header carries sha256=<hex>, the HMAC-SHA256 of the raw request body with the standup's signing secret. Copy it from the standup's Settings → Outbound webhook → Show signing secret (admins and that standup's managers), or fetch it with GET /api/v1/standups/:id/webhook/secret. It is derived from SECRET_KEY and the standup's id, so it changes only when SECRET_KEY does.

Verify it in your receiver and reject anything that doesn't match:

js
const expected = 'sha256=' + crypto.createHmac('sha256', SECRET).update(rawBody).digest('hex');
crypto.timingSafeEqual(Buffer.from(header), Buffer.from(expected));

Data ​

All state — standups, participants, admins, runs, submissions, blockers, app settings — lives either in a single SQLite file (DB_PATH, the default) or in your own PostgreSQL (DATABASE_URL). Schema migrations run automatically on startup in both modes. Backups and upgrades: Operations.

Managed Postgres TLS: RDS / Cloud SQL / Neon / Supabase present a certificate signed by their own CA. AsyncUp treats sslmode=require as "encrypt but don't verify the cert" (the libpq default every other client uses), so DATABASE_URL=…?sslmode=require connects out of the box. For strict verification set DB_SSL=verify-full and point DB_SSL_CA at the provider's CA bundle.

Stored secrets are encrypted, so backups are safe to ship off-box as long as SECRET_KEY stays out of them. Graceful shutdown on SIGTERM included.
